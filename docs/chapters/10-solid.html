CHAPTER 10 · WEEK 10

The SOLID principles

Five guidelines from Robert C. Martin for designs that stay understandable, flexible and maintainable. They are not rules to recite — each one removes a specific, nameable failure. We apply all five to the same class and watch it improve.

  • State each principle and the failure it prevents
  • Spot a violation in code you did not write
  • Apply the matching refactor
  • Explain when a principle costs more than it saves

10.1 — The five at a glance

PrincipleOne sentencePrevents

Everything in this chapter is a version of one idea. Isolate change. A requirement will move; the only question is how many files have to move with it. Each principle shrinks that number.

10.2 — One class, five refactors

Here is an Order class that adds items, totals the bill and takes payment by debit or credit. It works. Step through and watch each principle remove one concrete problem — and note that each step leaves a new problem, which is what motivates the next one.

10.3 — S · Single Responsibility

A class should have one and only one reason to change.

How to test it: list the reasons this class might need editing. The original Order had three — the basket rules, the pricing rules, the payment rules. Three reasons, three responsibilities, one class.

Two supporting ideas go with it. Cohesion: the members of a class should be closely related to one another. Coupling: a class should depend on as few others as possible.

◆ It applies to methods too

  • One method, one job.
  • Roughly one screen — say under 15 lines, as appropriate.
  • About three parameters; more usually means the method is doing too much.
  • One condition per if/else.
  • One calculation per calculation.
Do not overdo it. “One reason to change” is not “one method per class”. Splitting Account into AccountBalance, AccountNumber and AccountOwner raises coupling and helps nobody. The unit is a reason to change, not a field.

10.4 — O · Open–Closed

Software components should be closed for modification but open for extension.

You met this in chapter 5. Once a class is written and tested, do not edit it — extend it. The reason is risk arithmetic: editing a tested class puts every existing caller at risk; adding a new class risks nothing, because nothing calls it yet.

In the payment example, PaymentProcessor becomes an abstract base class with one abstract pay(). Debit and credit become subclasses. When PromptPay is added, it is a new file and no existing line changes.

The giveaway symptom. An if/elif chain on a type string — if payment_type == 'debit' … elif payment_type == 'credit' — is almost always an Open–Closed violation. Every new type means editing that function. Replace the branch with polymorphism.

10.5 — L · Liskov Substitution

We present a way of defining the subtype relation that ensures that subtype objects preserve behavioural properties of their supertypes. Barbara Liskov

In working terms: anywhere the base class is accepted, a subclass must work. A subclass may add capability; it must never take capability away or change the meaning of what it inherited.

✗ the subclass changes the deal
class PaymentProcessor(ABC):
    @abstractmethod
    def pay(self, order, security_code): ...

class PromptPayProcessor(PaymentProcessor):
    def pay(self, order, security_code):
        # PromptPay has no security code —
        # this parameter is really a phone number
        print(f'Phone: {security_code}')
        order.status = 'paid'
The parameter now means something different for this subclass. Any caller that passes a real security code is silently wrong.
✓ the contract holds for all
class PaymentProcessor(ABC):
    @abstractmethod
    def pay(self, order): ...        # order only

class PromptPayProcessor(PaymentProcessor):
    def __init__(self, phone):
        self.__phone = phone          # its own credential

    def pay(self, order):
        order.status = 'paid'
Credentials belong to each processor, supplied at construction. pay(order) means exactly one thing everywhere.

Other classic violations to recognise:

  • A subclass that raises NotImplementedError for an inherited method
  • A subclass that narrows what the parent accepted (parent takes any number, child rejects negatives)
  • A subclass that strengthens what the caller must do first (an extra connect() the parent never needed)
  • Square(Rectangle) — setting the width secretly changes the height, so code written against Rectangle breaks

10.6 — I · Interface Segregation

Interfaces should be separated according to their use, rather than one general interface shared by many classes.

No class should be forced to implement a method it does not use. The symptom is unmistakable: a method whose entire body is pass, or raise Exception('not supported').

the parking lot from the slides violation
class ParkingLot:
    def park_vehicle(self, v): ...
    def unpark_vehicle(self, v): ...
    def get_capacity(self): ...
    def calculate_fee(self, v): ...
    def do_payment(self, v): ...

class FreeParkingLot(ParkingLot):
    def park_vehicle(self, v): ...
    def unpark_vehicle(self, v): ...
    def get_capacity(self): ...
    def calculate_fee(self, v):
        raise NotImplementedError('parking here is free')
    def do_payment(self, v):
        raise NotImplementedError('parking here is free')

The fix: take calculate_fee and do_payment out of ParkingLot, and create PaidParkingLot and FreeParkingLot, with only the paid one carrying the money methods.

The same problem, in the payment example

Adding SMS authentication to the abstract PaymentProcessor forces credit-card payments — which do not use SMS — to implement auth_sms(). There are two good fixes, and you should be able to argue for either:

Fix 1 · split the interface

Add PaymentProcessorSMS(PaymentProcessor) that declares auth_sms(). Debit and PayPal extend it; credit extends the plain one. Simple, but the hierarchy grows a branch per combination of features.

Fix 2 · composition

Make an SMSAuthorizer class and hand it to the processors that need it. No new branches, and the authoriser can be swapped or faked in a test. This is the fix that leads straight into D.

10.7 — D · Dependency Inversion

High-level modules should not depend upon low-level modules. Both should depend upon abstractions.
Abstractions should not depend upon details. Details should depend upon abstractions.

First, the vocabulary. A high-level module is the code that runs the overall job — like a site supervisor on a building project, who decides what must happen but does not lay the cement themselves. A low-level module is the code that does the concrete work — the person laying the cement.

A well-designed system lets either side be replaced. The supervisor can direct anyone who knows how to lay cement; the cement layer can work on any site. Neither is welded to the other.

✗ the high level builds the low level
class SmartPhone:
    def __init__(self):
        self.__bt = BluetoothDevice()   # welded in

    def connect(self):
        return self.__bt.pair()

# Want to test without real Bluetooth?  You can't.
# Want to support NFC?  Edit SmartPhone.
✓ the collaborator is handed in
class SmartPhone:
    def __init__(self, device):      # any device that can pair()
        self.__device = device

    def connect(self):
        return self.__device.pair()

phone = SmartPhone(BluetoothDevice())
phone = SmartPhone(NfcDevice())      # no change to SmartPhone
phone = SmartPhone(FakeDevice())     # testable

This pattern — create the object outside and pass it in — is called dependency injection. It is the same move as SMSAuthorizer in the walkthrough, and the same move as composition in chapter 6. You have now seen it three times under three names, which is a sign of how central it is.

◆ Lab 10 — apply SOLID to your group's application

Take your mini-project as it stands and audit it. For each finding, write three sentences: the principle, the evidence, and the fix.

  • S — which class has more than one reason to change? List its reasons.
  • O — which if/elif on a type would grow when you add a feature?
  • L — does any subclass raise, ignore, or re-interpret an inherited method?
  • I — is any class implementing a method it never uses?
  • D — does any class construct a collaborator it could instead be handed?
This is also Assignment 2, phase 2. The legacy-code review asks for at least three code smells with proposed solutions. “Order has three reasons to change, which violates SRP; extract the payment logic into a PaymentProcessor hierarchy” is the kind of sentence that earns marks. “The code is messy” is not.

10.9 — When a principle costs more than it saves

These are guidelines, not laws, and applying them without judgement produces its own kind of bad code.

  • An abstract base class with one subclass is pure overhead. Wait for the second case.
  • Splitting a class with one reason to change raises coupling and helps nobody.
  • Injecting every dependency turns constructors into ten-parameter lists and moves the complexity into whoever builds the object.
  • Designing for extensions nobody asked for is speculation. You will usually guess wrong, and then carry the abstraction forever.

The honest rule: apply a principle when you can name the specific change it protects you from. If you cannot, write the simple version and refactor when the second case actually arrives.
