CHAPTER 9 · WEEK 9

Multiple inheritance, MRO & mixins

Python lets a class have more than one parent. That is powerful and it is a trap: the diamond problem, constructors that run twice, and arguments that go missing. Here is how to use it without being bitten.

  • Predict which method Python runs, using the method resolution order
  • Explain the diamond problem and why super() solves it
  • Pass differing argument sets up a hierarchy with **kwargs
  • Use a mixin to add behaviour without claiming an is-a relationship
  • Raise and catch your own exception classes instead of printing errors

9.1 — Inheriting from more than one class

Many languages forbid this. Python allows it: list the parents, separated by commas, and the subclass gets the abilities of all of them.

two parents
class Clickable:
    def on_click(self):
        print('clicked')

class Drawable:
    def draw(self):
        print('drawing')

class Button(Clickable, Drawable):      # both
    pass

b = Button()
b.on_click()
b.draw()

You can also inherit from Python's own built-in types — useful for adding one method to a list:

extending a built-in
class SearchableList(list):
    def search(self, value):
        for i, item in enumerate(self):
            if item == value:
                return i
        return -1

names = SearchableList(['ann', 'ben', 'cate'])
names.append('dan')          # everything list can do
print(names.search('cate'))  # 2 — plus our own

9.2 — Method resolution order

If two parents both define find_area(), which one runs? Python answers with the method resolution order (MRO): a flat list of classes to search, in order, stopping at the first match.

The basic rule is depth-first, left to right: look at the class itself, then its first parent and that parent's ancestors, then the second parent, and so on. With a simple tree there is nothing to think about.

inspecting the MRO
class A: pass
class B(A): pass
class C(A): pass
class D(B, C): pass

print(D.__mro__)
# (D, B, C, A, object)

for cls in D.__mro__:
    print(cls.__name__)
Use it when you are stuck. If a call is reaching a method you did not expect, print YourClass.__mro__. The answer is always in that list, read left to right.

9.3 — The diamond problem

Trouble starts when both parents inherit from the same grandparent. The class graph is diamond-shaped, and a naive depth-first walk would reach the grandparent twice. Python's MRO linearises it so each class appears exactly once — but only if you call up with super().

Switch between the two styles below and compare the call order and the counter.

What “the base ran twice” costs you in practice. A counter is doubled. A list receives two copies of the same item. A database connection is opened twice and one is never closed. A file is written twice. None of these raise an error — they just produce wrong results, later.

9.4 — super() is not “my parent”

This is the single most misunderstood thing in the chapter. super() does not mean “the class in my parentheses”. It means the next class in the MRO of the object that is actually running.

In the diamond above, LeftSubclass.call_me() calls super().call_me() — and control goes to RightSubclass, which is not its parent at all. It went there because, in Subclass's MRO, RightSubclass comes after LeftSubclass. That is exactly what makes each class run once.

9.5 — When the parents want different arguments

The second classic problem. Contact wants a name and an email, AddressHolder wants a street, city, state and postcode, and Friend inherits both and adds a phone number. Calling the parents by name works. Switch to super() and it breaks — because super().__init__() runs one chain, and each class must pass along what it does not use.

✗ fixed parameter lists
class Contact:
    def __init__(self, name, email):
        self.name = name
        self.email = email

class AddressHolder:
    def __init__(self, street, city, state, code):
        self.street = street
        ...

class Friend(Contact, AddressHolder):
    def __init__(self, name, email, street,
                 city, state, code, phone):
        super().__init__(name, email)
        self.phone = phone

# TypeError: __init__() missing 4 required
#            positional arguments
Only one chain runs, and AddressHolder never gets its arguments.
✓ every class takes **kwargs
class Contact:
    def __init__(self, name='', email='', **kwargs):
        super().__init__(**kwargs)      # pass the rest along
        self.name = name
        self.email = email

class AddressHolder:
    def __init__(self, street='', city='',
                 state='', code='', **kwargs):
        super().__init__(**kwargs)
        self.street = street
        ...

class Friend(Contact, AddressHolder):
    def __init__(self, phone='', **kwargs):
        super().__init__(**kwargs)
        self.phone = phone

f = Friend(name='Terry', email='terry@abc.co',
           phone='081-234-5678', street='Sukhumvit',
           city='BKK', state='BKK', code=10520)
One super().__init__(**kwargs) per class. Each takes the arguments it understands and forwards the rest. Both parents are initialised.

The rules that make this work:

  • Every class in the hierarchy declares only the arguments it uses, then **kwargs
  • Every class calls super().__init__(**kwargs) exactly once
  • Give defaults, so a class can be built without every argument
  • Call with keyword arguments at the top, never positional
The subtlety the slides raise. In Friend.__init__(self, phone='', **kwargs), phone has been pulled out of kwargs. If a class further up also needs phone, it will never see it. Fixes: leave it in kwargs and read kwargs['phone']; put it back with kwargs['phone'] = phone or kwargs.update(...); or forward it explicitly with super().__init__(phone=phone, **kwargs).

9.6 — Mixins

A mixin is a small class that exists only to lend behaviour to others. It is not a parent in the is-a sense, and you would never instantiate one. It is the honest way to use multiple inheritance.

Suppose Vehicle has subclasses Car and Boat, and you want a radio in the car but not in the boat. Putting the radio in Vehicle gives it to the boat as well. Putting it only in Car means duplicating it when a Bus arrives.

a mixin adds a capability to exactly the classes that want it
class Vehicle:
    def __init__(self, position):
        self.position = position
    def travel(self, destination):
        ...

class RadioUserMixin:
    def __init__(self, **kwargs):
        super().__init__(**kwargs)
        self.radio = Radio()
    def play_song_on_station(self, station):
        self.radio.set_station(station)
        self.radio.play_song()

class Car(Vehicle, RadioUserMixin):   # a car IS a vehicle, and HAS a radio
    pass

class Boat(Vehicle):                  # no radio
    pass
the DictMixin from the slides
class Person:
    def __init__(self, name):
        self.name = name

class DictMixin:
    def to_dict(self):
        return self._traverse_dict(self.__dict__)

    def _traverse_dict(self, attributes):
        return {k: self._traverse(k, v) for k, v in attributes.items()}

    def _traverse(self, key, value):
        if isinstance(value, DictMixin):
            return value.to_dict()
        elif isinstance(value, dict):
            return self._traverse_dict(value)
        elif isinstance(value, list):
            return [self._traverse(key, v) for v in value]
        elif hasattr(value, '__dict__'):
            return self._traverse_dict(value.__dict__)
        return value

class Employee(DictMixin, Person):
    def __init__(self, name, skills, dependents):
        super().__init__(name)
        self.skills = skills
        self.dependents = dependents

e = Employee(name='John',
             skills=['Python', 'Project Management'],
             dependents={'wife': 'Jane', 'children': ['Alice', 'Bob']})
print(e.to_dict())
  • Name it SomethingMixin so readers know it is not a real parent.
  • Put the mixin first in the base list when its methods should win.
  • Keep it small — one capability per mixin.
  • A mixin should not require state the host class does not have.

9.7 — Exceptions instead of printing

Up to now a validation failure in a setter might have printed a message. That is not good enough: a class must not print (chapter 3), and the caller cannot act on a print. Raise an exception instead — and define your own class for it, so callers can catch exactly the thing they know how to handle.

✗ printing
class Account:
    def withdraw(self, amount):
        if amount > self.__balance:
            print('Not enough money')
            return
        self.__balance -= amount

acct.withdraw(5000)
# printed somewhere; the caller has no idea
# whether the withdrawal happened
✓ your own exception class
class InsufficientFunds(Exception):
    def __init__(self, balance, requested):
        self.balance = balance
        self.requested = requested
        super().__init__(
            f'balance {balance} < requested {requested}')

class Account:
    def withdraw(self, amount):
        if amount > self.__balance:
            raise InsufficientFunds(self.__balance, amount)
        self.__balance -= amount

try:
    atm.withdraw(card, pin, 5000)
except InsufficientFunds as e:
    screen.show(f'Short by {e.requested - e.balance}฿')

Notice the exception carries data, not just a message. The ATM can tell the customer how much short they are without re-reading the balance — and a test can assert on the numbers.

The honest summary. Most of the time you do not need multiple inheritance, and reaching for it is a sign that composition would be cleaner. Keep it for mixins, where the intent is explicit and the surface is small.
