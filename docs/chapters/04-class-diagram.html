CHAPTER 4 · WEEK 4

Class diagrams

A class diagram is not documentation you write after the fact. It is the thing you write the program from. Two parts only: the classes, and the relationships between them — but the relationships are where all the marks are.

  • Read and draw class notation with correct access markers
  • Tell association, dependency, aggregation and composition apart, and justify the choice
  • Attach multiplicities and translate them into Python data structures
  • Design a class diagram from a written specification using a repeatable five-step method

4.1 — Class notation

A class box has three compartments: the name, the attributes (what it stores) and the methods (what it can do). Each member carries an access marker.

Draw it before you code it. On a diagram you can see that ATM has drifted into storing a balance in about four seconds. In 300 lines of Python you will not notice for a week.

4.2 — The four relationships

Every pair of related classes gets exactly one line, and the kind of line states how tightly they are bound. Pick the weakest line that is still true — weaker coupling is always better.

Association — “A keeps a reference to B”

The normal case. When you write the code, one class gains an attribute holding the other. Associations come in three shapes:

  • Unary (one-way) — only one side stores the other. A Subject must know its Teacher; a teacher does not need a list of subjects.
  • Binary (two-way) — both sides store each other. A student has one advisor; an advisor has a list of advisees. Draw it only when you really need to navigate both ways — every extra reference is another thing to keep in sync.
  • Self-association — a class related to its own kind: a boss and subordinates, a mentor and mentee, friends.

Put a verb on the line. Student — enrols in → Subject lets the diagram tell a story a non-programmer can check.

Dependency — “A uses B, briefly”

Weaker than association: B appears only as a method parameter and is never stored. This is the relationship students miss most often, and it is directly worth marks in Lab 3, where the brief says the ATM stores nothing but its own cash.

✗ drawn as association
class ATM:
    def __init__(self, atm_id, cash):
        self.__atm_id = atm_id
        self.__cash = cash
        self.__card = None        # ← stored

    def insert_card(self, card):
        self.__card = card
Now the ATM holds somebody's card after they walk away, and two ATMs can disagree about which card is in which machine.
✓ drawn as dependency
class ATM:
    def __init__(self, atm_id, cash):
        self.__atm_id = atm_id
        self.__cash = cash        # the only state it owns

    def withdraw(self, card, pin, amount):
        if not card.verify_pin(pin):
            return 'Invalid PIN'

The card arrives, is used, and is gone. The relationship is a dashed arrow.

The test that always works: delete the owner in your head. Does the part still mean anything? A song does, so Playlist–Song is aggregation. An order line without its order is nonsense, so that is composition.

4.3 — Multiplicities

A relationship also has a number. Multiplicity is written at each end and answers: how many of this class can be at this end of the line?

NotationMeaningWhat you write in Python
1exactly oneself.__teacher = teacher
0..1zero or oneself.__card = None until one is issued
0..* or *any number, including noneself.__students = []
1..*at least one[] plus a rule that forbids emptying it
n..mbetween n and m[] plus a length check in the setter
This is the most practical thing on the diagram. Multiplicity tells you the data structure. 1 means a single variable. 0..* means a list. If you draw the multiplicities properly, half of __init__ writes itself.
reading multiplicities straight into code
# Subject —— 0..* ———— 1 —— Teacher      (a subject has exactly one teacher)
# Member  —— 1 ——— 0..10 —— BookLending  (a member may borrow up to 10 books)

class Subject:
    def __init__(self, subject_id, name, credit):
        self.__teacher = None          # '1'  -> one slot

class Member:
    MAX_BOOKS = 10
    def __init__(self, member_id):
        self.__lendings = []           # '0..10' -> a list…

    def borrow(self, lending):
        if len(self.__lendings) >= Member.MAX_BOOKS:   # …plus the upper bound
            return 'Limit reached'
        self.__lendings.append(lending)

4.4 — Every object needs a container

An object with nothing pointing at it is unreachable, and Python's garbage collector will throw it away. So before you finish a diagram, ask of every class: who holds the list?

Sometimes the answer is another domain class — BookItems live inside their Book. When nothing suitable exists, create a class to represent the system itself: Library, School, Bank. It owns the master lists and the methods that span several classes.

4.5 — Class attributes, static and class methods

Not every piece of data belongs to an instance. A class attribute is shared by the whole class — a limit, a counter, a constant. It is written above __init__ with no self., and read through the class name.

class attribute vs instance attribute
class Backpack:
    max_num_items = 5          # class attribute — one copy, shared
    count = 0

    def __init__(self, owner):
        self.owner = owner      # instance attribute — one per object
        Backpack.count += 1     # count every object ever made

print(Backpack.max_num_items)   # 5  — no instance needed
b = Backpack('John')
print(b.max_num_items)          # 5  — instances can read it too
print(Backpack.count)           # 1

static and class methods in practice
class Student:
    def __init__(self, first, last, weight_kg):
        self.__first = first
        self.__last = last
        self.__weight_kg = weight_kg

    @staticmethod
    def kg_to_pound(kg):              # pure conversion, no self needed
        return kg * 2.20462

    @classmethod
    def from_full_name(cls, full_name, weight_kg):   # second constructor
        first, last = full_name.split(' ', 1)
        return cls(first, last, weight_kg)

print(Student.kg_to_pound(50))                   # 110.231 — no instance
s = Student.from_full_name('John Smith', 68)     # a different way to build one

4.6 — Designing from a specification: five steps

This is the method the slides use on the library system, and the one the staff expect to see you follow in the labs. Work it in order; do not jump to relationships before you have attributes.

  1. Find the classes. Underline the nouns in the specification. Some are obvious because they are tangible — Member, Librarian, Book, BookRack. Some hide in a sentence: “in the case where there are multiple copies of the same book, each copy is called a book item” gives you BookItem. Events are classes too: a borrowing becomes BookLending, a reservation becomes BookReservation.
  2. Give each class its attributes. Only what that class is genuinely the expert on. A Book owns the ISBN, title, author and subject; a BookItem owns the item number, status and shelf location. Availability is per copy, so it goes on the item, not the book.
  3. Decide where every object is stored. BookItems can live inside their Book. Everything else needs a home, so create Library with users, books, book_racks, lendings and reservations.
  4. Define the methods. For each class ask: what processing does it owe, beyond getters and setters? Book.get_available_items(); BookItem.is_available() and checkout(); Member.get_total_book_checkout(), checkout_book_item(), reserve_book_item(), return_book_item(); Librarian.add_book_items(), add_member(). The container class ends up with the most: searches, overdue checks, and the processes that span classes.
  5. Set the relationships, one pair at a time. Take two classes, decide which of the four lines is true, and write the multiplicity at each end. Then move to the next pair. Do not try to see the whole web at once.
Where step 2 goes wrong. “The system must warn the user if a book is overdue.” That sentence tempts people into giving Book a warn_user() method. But a book knows nothing about who has it — the BookLending knows the due date, and the Library knows all the lendings. Put the behaviour where the data already is.

4.7 — Four design principles to judge a diagram by

Creator

Whoever uses an object most should be the one that creates and stores it. An Account creates its own Transactions and keeps them — not the ATM, which merely triggered one.

Information Expert

Give a responsibility to the class that already holds the data it needs. Deposits and withdrawals belong on Account, because Account is the only class that knows the balance.

Low Coupling

Minimise how much each class must know about others. Every reference you add is a change that can propagate. Prefer dependency over association, and association over inheritance, when all three would work.

Controller

Separate the classes that hold domain data (Account, ATM) from the one that coordinates them (Bank). The controller receives requests from the UI and distributes the work. Large systems have several — payment, delivery, and so on.

Low coupling, made concrete. Suppose an ATM both deposits and withdraws, and you now add a rule about deposit limits. If the rule lives in ATM, you must change it in the counter service and the mobile app too. If it lives in Account, you change it once and every channel obeys it. Where you put a rule decides how far a change can spread.
