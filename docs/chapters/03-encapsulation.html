CHAPTER 3 · WEEK 3

Encapsulation, access levels and methods

Capsule + en — to put in one piece. Bind the data to the code that guards it, and stop everything else from reaching in. This is the pillar that makes the other three safe.

  • Describe what goes wrong when an attribute is public, with a concrete failure
  • Use Python's naming conventions for public, protected and private, and explain what Python really enforces
  • Write setters that validate, and decide which attributes need a getter or setter at all
  • Use @property to get attribute syntax with method safety

3.1 — The failure encapsulation prevents

In chapter 2 we wrote stu1.name = 'Johnny' and nothing objected. That is the problem. If a Student's data can be edited from anywhere, then everywhere is responsible for keeping it valid — which means nowhere is.

The real argument, stated precisely. Encapsulation does not stop bugs from being written. It moves the moment of failure to the line that is wrong, instead of somewhere far away and much later. A ValueError at s.gpa = -5 takes a minute to fix. A wrong scholarship list discovered in week 14 takes a day to trace.

Encapsulation has a consequence with its own name: information hiding — limiting access to data that was never meant to be touched from outside. Accessing instance attributes with dot notation from outside the class violates it, so we take that ability away.

3.2 — Three levels of access

Most object-oriented languages divide attributes into two or three levels. Java enforces them with keywords and the compiler refuses to break the rules:

Some textbooks say “public and non-public” and then split non-public into the two underscore forms. Same idea, different vocabulary. Either way: do not reach for a variable beginning with _ from outside its class, even though Python will let you.

3.3 — Getters and setters

If attributes are private, outside code needs a door. Those doors are methods: a getter reads, a setter writes. The naming convention is get_ / set_ followed by the attribute name.

A getter is nearly trivial. The setter is where the value is. It is the one place that can refuse a bad value — and because it is the only way in, that refusal is total.

Student, properly encapsulated good
class Student:
    def __init__(self, student_id, student_name):
        self.__student_id = student_id        # private
        self.set_student_name(student_name)   # validated even here

    def get_student_name(self):
        return self.__student_name

    def set_student_name(self, student_name):
        if not isinstance(student_name, str):
            raise ValueError('name must be text')
        if not student_name.replace(' ', '').isalpha():
            raise ValueError('name must be letters only')
        self.__student_name = student_name.strip()

    def get_student_id(self):
        return self.__student_id
        # note: no set_student_id — an id must never change

Which attributes get a getter or setter?

This is marked in the labs, and marks are deducted for the extra ones: if unnecessary setters or getters are found, points will be deducted.

The anti-pattern to avoid. Writing get_x() and set_x() for every single attribute recreates public attributes with extra typing, and gains nothing. If a setter has no validation and no side effect, ask whether the attribute should be settable at all. A balance with a plain setter is not an encapsulated balance — it is a public one in disguise.

3.4 — Methods

Beyond getters and setters, a class needs the methods that are actually its job. A method differs from a function in one way that matters: it can reach the state of the specific instance that called it. That is what self is for, and it is required even when there are no other parameters.

a method that does the class's real work
class Subject:
    def __init__(self, subject_id, subject_name, credit):
        self.__subject_id = subject_id
        self.__subject_name = subject_name
        self.__credit = credit
        self.__student_list = []

    def add_student(self, student):          # verb, snake_case
        if not isinstance(student, Student):
            return 'Error'
        if student in self.__student_list:
            return 'Already Enrolled'
        self.__student_list.append(student)
        return 'Done'

    def get_no_of_student(self):
        return len(self.__student_list)

    def _recalculate_section(self):          # protected helper
        ...
  • Name methods with a verb — they do something.
  • Use snake_case.
  • Prefix with a single _ if the method is only for internal use.
  • Methods may call one another through self: self._recalculate_section().
A lab rule with a reason. In a class, do not input values or print values directly — send parameter data in and get data back. A class that prints cannot be used by a GUI, a web request or a test. Treat every class as a service: it answers questions and performs actions; the caller decides how to display the result.

Method chaining

A method that ends with return self hands the instance back, so the next call can be written straight after it.

without chaining
class Pizza:
    def __init__(self, size):
        self.__size = size
        self.__toppings = []

    def add_topping(self, t):
        self.__toppings.append(t)

p = Pizza('L')
p.add_topping('cheese')
p.add_topping('ham')
p.add_topping('basil')
with return self
class Pizza:
    def __init__(self, size):
        self.__size = size
        self.__toppings = []

    def add_topping(self, t):
        self.__toppings.append(t)
        return self              # hand the instance back

p = Pizza('L').add_topping('cheese') \
              .add_topping('ham') \
              .add_topping('basil')

3.5 — Two ideas you need first: closures and decorators

@property is built from these two. You will not be examined on writing your own decorators, but you must be able to read one.

Closures

A closure is an inner function that is returned from an outer function and still remembers the outer function's variables. Those remembered variables are called free variables.

one source, two different behaviours
def multiplier(factor):          # outer
    def inner(x):                # inner, nested
        return x * factor        # 'factor' is a free variable
    return inner                 # returned, not called

double = multiplier(2)
triple = multiplier(3)
print(double(10), triple(10))    # 20 30

Three conditions, all required: the functions are nested; the inner one references a variable of the outer one; the inner one is returned from the outer one.

Decorators

A decorator is a function that takes a function, wraps extra behaviour around it, and returns the replacement. The @ symbol is a shortcut for exactly that.

the long way
def make_pretty(func):
    def wrapper():
        print('***')
        func()
        print('***')
    return wrapper

def ordinary():
    print('I am ordinary')

ordinary = make_pretty(ordinary)
ordinary()
the @ shortcut — identical
def make_pretty(func):
    def wrapper():
        print('***')
        func()
        print('***')
    return wrapper

@make_pretty
def ordinary():
    print('I am ordinary')

ordinary()

3.6 — @property: attribute syntax, method safety

Getters and setters give you safety but cost you readability: s.set_gpa(s.get_gpa() + 1) is noise. Python's property gives back the natural syntax while keeping the method underneath. When you read d.age Python runs the getter; when you assign to it, Python runs the setter.

Why the decorator form is the one to use. Building a property the old way — age = property(get_age, set_age) — leaves get_age and set_age still callable, so there are two ways to change the same attribute. With @property and @age.setter there is exactly one. Fewer doors, fewer bugs.
the shape to memorise
class Dog:
    def __init__(self, age):
        self.age = age          # runs the setter

    @property                   # ← the getter
    def age(self):
        return self.__age

    @age.setter                 # ← the setter, same name
    def age(self, value):
        if not isinstance(value, int) or not 0 < value < 30:
            raise ValueError('invalid age')
        self.__age = value

A property with only a getter and no setter is a read-only attribute — the right shape for student_id, account_number, isbn. Assigning to it raises AttributeError, which is exactly what you want.

3.7 — Choosing correctly

You want…UseNot
An attribute nobody outside may read or writeself.__x, no accessora getter “just in case”
A value that is read but never changed@property getter onlya public attribute
A value with rules about what is valid@property + @x.settera public attribute and hope
A change that is more than an assignmenta named method — deposit(amount)set_balance()
A subclass to reach it, but not outsidersself._xself.__x, which the subclass cannot see either
The last row catches people out. Name mangling is per-class. If Account stores self.__balance, then SavingsAccount(Account) cannot read self.__balance either — it would look for _SavingsAccount__balance. Use a single underscore for anything a subclass legitimately needs, or go through the parent's getter.
