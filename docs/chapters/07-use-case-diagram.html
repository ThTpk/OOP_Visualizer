CHAPTER 7 · WEEK 7

Finding requirements & use case diagrams

Requirements are the precursor of software: get them wrong and everything downstream is wrong, no matter how good the code is. This chapter is about discovering what to build, and drawing the scope.

  • Use personas, user stories and a definition of done to capture a requirement
  • Run a domain storytelling session and read the resulting picture
  • Draw a use case diagram with actors, a system boundary and relationships
  • Choose correctly between «include», «extend» and generalization
  • Turn a domain story into a first class diagram

7.1 — Why this is the hardest job in the project

Finding requirements decides what the software is. If they are incomplete or wrong, the system is faulty however well it is built — and the fault is discovered at the end, when it is most expensive.

It is also the skill that is hardest to hire and hardest to train, because it is not technical. It is listening to someone describe their own job, noticing what they left out because it is obvious to them, and writing it down in a form a developer can act on.

Why your mini-project needs this. You will be marked on whether the application does what the specification said. Teams that skip requirements discover in week 14 that they built a feature nobody asked for, and omitted one everybody assumed.

7.2 — Three tools for finding requirements

Persona

A fictional profile standing for one group of users. Worth the effort for software with a broad audience — Shopee, banking, social, e-commerce — where different groups want different things. A persona has:

Demographics & behaviour

age, job, interests, how they use technology

Goal

specific, and about this software. For a travel app, a travel goal.

Frustration

the pain point — what they want but cannot get today

The frustration is the most useful field: it is where features come from. “I want a trip plan that suits me without spending hours researching” is a feature request in disguise.

User stories

A one-sentence format that forces you to name the role, the want and the reason.

the template, and an example
As a   <role>
I want <capability>
So that <benefit>

As a    buyer at a clothing store
I want  to compare two shirts side by side
So that I can choose without opening two tabs

A story alone is too vague to build from, so each one gets a Definition of Done — the checklist that says when it is finished:

  • The system has a checkbox for selecting products to compare, and no more than 2 can be selected
  • There is a “Compare” button which opens a new window showing the 2 products side by side
  • The comparison shows price, size, colour and material in aligned rows

Without the DoD, “so that I can choose” is an opinion. With it, it is testable — and the marker can check it.

Domain storytelling

A technique by Stefan Hofer and Henning Schwentner for building shared understanding between the owner of a business and the people writing its software. You draw the story of how the work happens today, together, in the room, using three symbols only:

Actor

a person or system that does something — moviegoer, cashier

Work object

a thing that is not a person — seating plan, ticket, showtime

Activity

a numbered arrow joining them — tells, looks at, gives

  • Domain stories revolve around the actor — who does what, with what, and with which other actors.
  • Read every arrow aloud. Each should form a complete sentence. That is the quality check.
  • Cover special cases too: what happens when the show is sold out? The cashier suggests another film or time — and that is a feature you would otherwise have missed.
  • Include the back-office actors, not only the customer: somebody loads films and showtimes into the system.
  • When the picture gets crowded, draw a second diagram of the sub-stories — buy/sell tickets, buy/sell food, admission, screening — and group them.

Tools: paper works. So does diagrams.net or Miro. There is also egon.io, built specifically for domain storytelling, and domainstorytelling.org for the method itself.

It looks slow. It is not. Drawing the story once, with the customer in the room, is faster than four rounds of “actually, it also has to…” discovered during development.

7.3 — The use case diagram

The standard diagram for saying what the system can do and who can do it. It is deliberately high-level: no screens, no data, no order of events. Two basic components:

  • Actor — one group of users, drawn as a stick figure. An actor does not have to be a person: a payment gateway or a scheduled job is an actor. Draw each actor once.
  • Use case — something an actor can do, drawn as an ellipse and named with a verb.

A rectangle around the use cases marks the system boundary — what you are building, and by omission, what you are not.

The three relationships

RelationshipMeaningTestExample
«include» The base use case always performs the included one. Without it the base cannot complete. “Can the first finish without the second?” → No Book Ticket includes Select Seat; Checkout includes Calculate Total
«extend» Optional extra behaviour added on top of a base use case, under some condition. “Does it only sometimes happen?” → Yes Apply Coupon extends Pay; Add to Wishlist extends View Product
Generalization One job can be done in more than one way; or one actor is a special kind of another. “Is this a kind of that?” → Yes Pay by Card / Pay by Cash generalise to Pay; Librarian is a kind of Member
The direction of «extend» catches almost everyone. The optional use case is the source; the base is the target. Write it as a sentence — “Apply Coupon extends Pay” — and the arrow runs the way the sentence reads. For «include», “Book Ticket includes Select Seat” runs the same way, so the arrow points at the included use case. Both arrows follow the sentence.

7.4 — From a domain story to a use case diagram

The activities in your domain story become candidate use cases. Group the ones that belong to a single self-contained task:

Domain story activitySystem responseUse case
Customer selects a filmshow showtimesView Movie Detail / Select Show
Customer selects a showtimeshow the seating plan
Customer selects a seatconfirm the reservationSelect Seats
Customer paysissue the ticketPay for Tickets

Then add what the story implied but did not show: Search Movie, Apply Coupon during payment, View / Cancel Booking — and the back-office cases: adding and editing films, adding, editing and cancelling showtimes.

Guidelines for writing use cases

  1. One use case = one self-contained activity. Roughly the work of one page in an application.
  2. Watch the buttons. Every button on a screen is a candidate use case — even one that does not open a new page, such as Add to cart, because it changes something behind the scenes.
  3. Cover the whole system. Every part of it should appear somewhere on the diagram.
  4. Then add «include» — does this use case always require another?
  5. Then add «extend» — can this use case continue from another, sometimes?
  6. Name every use case with a verb. Book Ticket, not Booking.

7.5 — Use case descriptions

The diagram shows scope but not detail. For the main use cases, write a description. You do not need one for every use case — only the ones that carry real logic.

Use Case NameMovie Ticket Booking (Create Booking)
ActorCustomer, Front Desk Officer
DescriptionBooking a ticket for a customer who wants to see a film.
Normal CourseThe user selects the film and showtime they want and enters the booking process. The system displays the details of the selected film: date, showtime, language, cinema and theatre name. The system displays the seating layout, showing the seat types available and the price of each. When the user selects a seat, the system shows the selected seat and the total price. If the user selects a zone or a promotion, the system applies the discount or special offer.
Alternate CourseThe seats are full. · Two users select the same seat at the same moment.
The Alternate Course is where the marks are. Anyone can describe the happy path. “Two users select the same seat simultaneously” is the sentence that forces you to design a seat lock — a requirement that is invisible until somebody writes it down.

7.6 — From the domain story to a class diagram

The same picture feeds the structural design too. The mapping is direct:

In the domain storyIn the class diagramCinema example
Actora class — and if there are several similar ones, look for a common parentCustomer, Staff → both inherit User
Work objecta classMovie, Show, SeatingPlan, Seat, Reservation
Activitya method on the class that owns the dataselects a seat → Reservation.select_seat(seat)
(implied)classes the story never named but the structure needsa Seat is in a CinemaHall; a cineplex has many halls

Then apply the four design principles from chapter 4 — Creator, Information Expert, Low Coupling, Controller — to decide which class each method lands on.
