LABS · 50% OF THE LAB MARK

Weekly labs

Five briefs, each building on the one before. From Lab 3 onward the staff check your class diagram first and only then your code — so draw before you type.

The standing rules

These apply to every lab from Lab 2 onward. They are where marks are most often lost, usually by students whose program works perfectly.

  • No dictionaries for storage. A dict of records is the parallel-list problem with nicer syntax. Store instances in lists held by the owning class.
  • No data outside a class, and no duplicated data. If one fact appears in two places, one of them will go stale.
  • Every attribute private. Use __name. Getters and setters only where something outside genuinely needs them — unnecessary getters and setters lose marks too.
  • No input() and no print() inside a class. Pass parameters in, get values back. Treat every class as a service; the caller decides how to display things.
  • Store instances, not copies. A non-basic class must store instances of the basic classes, never duplicated fields.
  • Validate everything on the way in. Any value entering a class goes through a check.
  • Functions that act on a class's data must be methods of that class, not free functions.
  • Decide, for each class, what it may not store. If a piece of data fits nowhere, that is the signal to create a new class.
  • Add type hints. def withdraw(self, amount: float) -> bool: makes the intent explicit.
Why the rules are shaped like this. Every one of them is a specific bug prevented: stale copies, invalid state, untestable classes, data with no owner. Chapters 2, 3 and 4 explain each failure in detail.

Lab 1 — Object and class

week 2 chapter 2

Build a simple online-game character system with three classes — for example Player, Weapon and Armor. One of the three must be a component of another (a weapon belongs to a player).

  1. Define the attributes and behaviours of each class.
  2. Write all three classes including constructors. For behaviours, write the method names only and use pass as the body.
  3. Create three instances of each class.
  4. Set the relationships between them.
  5. Print the main object information in this shape:
=== Player 1 ===
Name: Hero_01
Level: 1
HP: 100
Weapon: Iron Sword (Damage: 10)
Armor: Leather Armor (Defense: 5)

=== Player 2 ===
Name: Archer_02
Level: 2
HP: 120
Weapon: Wooden Bow (Damage: 8)
Armor: Chain Mail (Defense: 10)

Then add a guild: the program must be able to say which guild each member belongs to and who the guild leader is.

The guild is the interesting part. A guild has members, and one of those members is the leader — which means the guild stores Player instances and one of them twice over. Make sure the leader is a reference to a member, not a second copy of their name.

week 3 chapter 3

Build the registration model with every attribute private: Student (student_id, student_name), Subject (subject_id, subject_name, credit), Teacher (teacher_id, teacher_name). You may add attributes and classes — one extra class is recommended, and the recommendation is not accidental.

Lab 3 — Class diagram (bank and ATM)

week 4 chapter 4 diagram checked first

The specification.

  • The bank opens accounts for users. There is one account type: savings. One user may open any number of accounts.
  • A user has a national ID (fictitious) and a full name. An account has an account number and an owner (an instance).
  • Each account may request one ATM card. The card has a card number, and the card holds the account number and a PIN.
  • Rates and limits: an ATM card costs 150฿ a year; the daily withdrawal limit is 40,000฿.
  • An ATM has a machine number and the cash in the drawer, defaulting to 1,000,000฿. The ATM stores nothing else. Banknote denominations are ignored.
  • Activities with the bank are done through ATMs only: deposit, withdraw and transfer. Withdrawals and transfers must not exceed the daily maximum.
  • Each transaction is recorded in the account: type (D deposit, W withdraw, TD transfer in, TW transfer out), amount, ATM number, and for transfers the other account number.

Tasks

  1. Draw the class diagram. Multiplicity is not required yet. Have the staff check it before you code.
  2. Write the program to match the diagram, under the standing rules above.
  3. Create the instances: 2 users with citizen ID 1-1101-12345-nn-0, where nn is the last two digits of your student ID (use nn+1 for the second user); 1 account each with a 10-digit account number; 1 ATM card per account with PIN 1234; 2 ATMs.
  4. After the test cases pass, have the staff check again and report whether the class diagram needed changing.

Test cases

  1. Insert card into ATM
  2. Deposit
  3. Deposit a negative amount
  4. Withdraw
  5. Withdraw more than the account balance
  6. Transfer
  7. Show statement
Two traps are deliberate. “The ATM will not store any information except the money in the machine” makes ATM–ATMCard a dependency, not an association. And “each transaction must be recorded in the account” makes Account–Transaction a composition. Get those two right and the rest follows.

Lab 4 — Inheritance (ATM 2)

week 5 chapter 5

Extend Lab 3's code rather than starting again. The bank has grown:

  • Two account types with different interest rates: savings 0.5%, fixed deposit 2.5%.
  • A new product, the debit card. It does everything an ATM card does and can also buy goods; purchases are recorded with code P (Paid).
  • A savings account may request one ATM card or one debit card.
  • Annual fees: ATM card 150฿, debit card 300฿.
  • ATMs now limit a single withdrawal to 20,000฿, and a transfer to 100,000฿.
  • A debit card can be used at an EDC terminal (machine number, merchant name) or electronically. Create a Merchant class that can accept electronic payment, and give each merchant its own EDC.
  • There are now three channels: the ATM (deposit, withdraw, transfer), the EDC or electronic payment (money moves from the payer's account to the merchant's), and the counter (deposit and withdraw).
  • Each transaction records the type, the amount, the resulting balance, and for a transfer the destination account.

Additional requirements

  • Use inheritance wherever the diagram shows an is-a relationship
  • Deposit uses the + operator — implement __add__
  • Withdraw uses the - operator — implement __sub__
  • Transfer uses a method called transfer
  • All payment uses a method called paid, in every case
  • Statements are displayed with a for loop over the account's transactions

Test cases

  1. Deposit using +
  2. Withdraw using -
  3. Transfer using transfer
  4. Pay at an EDC terminal using paid
  5. Pay electronically using paid
  6. Display a statement using for
Where inheritance belongs here. SavingsAccount and FixedDeposit are kinds of Account — different interest rules, one calculate_interest() overridden. DebitCard is a kind of ATMCard — everything the parent does, plus paid(). Merchant is not a kind of User unless it really opens accounts the same way; check the is-a sentence before you draw the triangle.

Lab 5 — Polymorphism (appointment system)

week 6 chapter 6

Three kinds of entry go in the diary:

TypeDataParticipants
One-time appointmentname, date, place, detailsalways has participants
Weekly appointmentname, weekday, place, detailsalways has participants
Eventname, date, place, detailsnone named — it is for everybody, and everybody is notified

An event differs from an appointment precisely in that it does not list participants, because the participants are everyone. That difference is what shapes the hierarchy.

What the program must do

  • Edit and delete appointments and events
  • Add participants to one-time and weekly appointments. Overlapping appointments are allowed — do not check for clashes
  • Give every appointment a notification. Each member chooses one channel: e-mail or SMS
  • Search all appointments and events in the system
  • Search by person — every appointment that person is in, plus all events
  • Send the notification for an appointment, using each recipient's chosen channel

Test cases

  1. Add — one-time #1 “Team Meeting #1”, 2024-03-15, Room A, with Jane Smith, Robert Johnson, Emily Davis · one-time #2 “Team Meeting #2”, 2024-03-17, Room B, same three · weekly “Weekly Meeting”, Wednesday, Room C, with John Doe, Robert Johnson, Emily Davis · event #1 “Company Party”, 2024-03-17, Conference Room · event #2 “Company Visit”, 2024-03-19, Conference Room. Then display everything.
  2. Edit — rename one-time #1 to “Team B Meeting #1”; move one-time #2 from Room B to Room C. Display everything.
  3. Delete — remove one-time #2. Display everything.
  4. Add participants — John Doe to “Team B Meeting #1”; Jane Smith to “Weekly Meeting”. Display everything.
  5. Search by person — “Robert Johnson”. The result must include the events as well.
  6. Notify — send the notification for “Team B Meeting #1”. Each recipient gets it by their own channel.
Two places polymorphism does the work. First, displaying a mixed list of appointments and events with one loop calling the same method. Second, notification: EmailNotifier and SMSNotifier both implement send(), and the sender never asks which one it has. If your code contains if member.channel == 'email', you have written the chapter 6 anti-pattern.
