CHAPTER 5 · WEEK 5

Inheritance

A subclass takes everything the superclass has and adds its own specifics. The reason is not elegance — it is that a shared rule should have exactly one place to be changed.

  • Apply the is-a test to decide whether inheritance is legitimate
  • Call a superclass constructor correctly with super()
  • Override a method, and say why overriding removes if statements
  • State the Open–Closed Principle and show a design that obeys it
  • Recognise when composition is the right answer instead

Here are several employee types, each written independently. They share an id, a name, an email, a phone number, an address, a hire date. Move the sliders and watch the two numbers that matter: how many lines, and how many files you must edit when a shared rule changes.

5.2 — Syntax and vocabulary

The class being inherited from is the superclass (or parent, or base). The class inheriting is the subclass (or child, or derived). In Python you put the parent in parentheses.

the whole syntax
class Animal:
    def __init__(self, name):
        self.name = name
    def move(self):
        print('moving')

class Dog(Animal):          # Dog inherits everything Animal has
    def bark(self):
        print('woof')

d = Dog('Rex')
d.move()                    # inherited from Animal
d.bark()                    # Dog's own
print(d.name)               # Animal's __init__ ran

Everything in Python already inherits from object. In older code you will see class Student(object): written out; modern Python omits it.

5.3 — The is-a test

A class may inherit only if two things are true:

  1. It really is a kind of the parent. A Truck is a kind of Car, so it may inherit from Car. A motorcycle is not a car, so it may not — however many attributes they share.
  2. It adds something specific. A superclass holds the general; the subclass holds the specific — a truck adds a load capacity. A subclass that adds nothing is just a longer name for the parent.
✗ inheriting for the fields
class Employee:
    def __init__(self, emp_id, name, salary): ...

class Payslip(Employee):     # a payslip is NOT an employee
    def __init__(self, emp_id, name, salary, month):
        super().__init__(emp_id, name, salary)
        self.month = month

# nonsense that the type system now permits:
payslips = [p for p in staff if isinstance(p, Employee)]
#            a payslip turns up in a list of employees
Shared fields are a coincidence, not a relationship. Everything that accepts an Employee will now silently accept a Payslip.
✓ association instead
class Employee:
    def __init__(self, emp_id, name, salary): ...

class Payslip:               # separate class, holds a reference
    def __init__(self, employee, month, gross):
        self.__employee = employee     # association
        self.__month = month
        self.__gross = gross

    def get_employee_name(self):
        return self.__employee.get_name()
A payslip refers to an employee. One fact, one place, and no false is-a claim.
Say it out loud. “A truck is a car.” ✓ · “A payslip is an employee.” ✗ · “A car has an engine.” → composition, not inheritance · “A dog is an animal.” ✓ If the sentence sounds wrong in English, the inheritance is wrong in code.

5.4 — Constructors across the hierarchy

There are three cases, and you must be able to tell them apart in the exam.

1 · Subclass has no __init__

It uses the superclass's constructor unchanged.

class Dog(Animal):
    def bark(self):
        print('woof')

d = Dog('Rex')   # Animal.__init__

2 · Subclass has its own, and does not call up

The parent's constructor never runs — the parent's attributes do not exist.

class Dog(Animal):
    def __init__(self, breed):
        self.breed = breed

d = Dog('Beagle')
d.name   # AttributeError

3 · Subclass extends the parent's

The usual and correct case.

class Dog(Animal):
    def __init__(self, name, breed):
        super().__init__(name)
        self.breed = breed

You will also see the parent called by name: Animal.__init__(self, name). It works for a single parent, but super() is the form to use — chapter 9 shows the bug the class-name form causes once more than one parent is involved.

Case 2 is the commonest silent bug in Lab 4. You add an __init__ to the subclass to store one extra field, forget super().__init__(…), and every inherited attribute vanishes. The error appears much later, as AttributeError in a method you did not touch.

5.5 — Method overriding

A subclass can redefine a method it inherited. Same name, same call, different body. Python looks on the object's own class first and only walks up the tree if it finds nothing.

the parent is searched only if the child has nothing
class Parent:
    def show(self):
        print('Inside Parent')

class Child(Parent):
    def show(self):                   # overrides Parent.show
        print('Inside Child')

Child().show()      # Inside Child
Parent().show()     # Inside Parent — the parent is unaffected

An override does not have to discard the parent's work. Call up first, then add:

extending rather than replacing
class ScienceTeacher(Teacher):
    def welcome_students(self):
        super().welcome_students()     # everything the parent does…
        print('Lab safety briefing at 9am')   # …plus our own

Overriding is what makes polymorphism possible, and that is where it pays off: a single loop can command a warrior, an archer and a mage without an if in sight.

5.6 — The Open–Closed Principle

Software components should be closed for modification, but open for extension.

Once a class is written and tested, do not touch it again. When something new is needed, add a subclass rather than editing the original. The reason is risk: an edit to a tested class can break every caller; a new class can break nothing, because nothing calls it yet.

✗ editing the original
class Polygon:
    def area(self, shape, *dims):
        if shape == 'triangle':
            return 0.5 * dims[0] * dims[1]
        elif shape == 'square':          # ← added last week
            return dims[0] ** 2
        elif shape == 'circle':          # ← added today
            return 3.14159 * dims[0] ** 2
Every new shape re-opens a class that already worked, so every shape re-tests every other shape.
✓ adding a subclass
class Polygon:
    def area(self):
        raise NotImplementedError

class Triangle(Polygon):
    def __init__(self, b, h): self.b, self.h = b, h
    def area(self): return 0.5 * self.b * self.h

class Square(Polygon):               # new file, nothing else touched
    def __init__(self, s): self.s = s
    def area(self): return self.s ** 2
Adding Square changed zero existing lines, so zero existing tests can break.
You meet this again in week 10. Open–Closed is the O of SOLID. The payment-processor example in chapter 10 is the same idea applied to a real refactor.

5.7 — Worked example: an RPG

Every character has a name, level, hp, mp, exp and a position, and every one can attack, use a skill, move, level up, gain exp and die. Those go in the superclass. What differs is how each does them:

Archerranged; power from dexterity + accuracy; spends arrowsMulti Shot (3), Trap (1), Aimed Shot (1)fast (×1.2), can shoot while moving
Mageranged magic; power from magic + intelligence; spends manaFireball (50), Teleport (30), Ice Shield (40)normal speed, teleports to escape
GameCharacter and one subclass
class GameCharacter:
    def __init__(self, name, level=1, hp=100, mp=50):
        self._name = name
        self._level = level
        self._hp = hp
        self._mp = mp
        self._exp = 0
        self._position = (0, 0)

    def attack(self):
        raise NotImplementedError('every character must define attack()')

    def gain_exp(self, amount):      # identical for everyone -> stays here
        self._exp += amount
        while self._exp >= self._level * 100:
            self._exp -= self._level * 100
            self.level_up()

    def level_up(self):
        self._level += 1
        self._hp += 10

    def is_dead(self):
        return self._hp <= 0


class Warrior(GameCharacter):
    def __init__(self, name, strength=10, **kw):
        super().__init__(name, **kw)
        self.__strength = strength
        self.__rage = 0

    def attack(self):                # overridden
        return self.__strength * 1.8

    def use_skill(self, skill):
        cost = {'charge': 20, 'shield_block': 30, 'whirlwind': 50}[skill]
        if self.__rage < cost:
            return 'Not enough rage'
        self.__rage -= cost
        return f'{self._name} uses {skill}'

When inheritance is not the answer: the buff system

Now add buffs — temporary boosts one character gives the team. Warrior has Battle Cry and Defensive Stance; Mage has Arcane Intellect and Magic Shield; Archer has Eagle Eye and Camouflage. The tempting move is to add six methods to the three character classes. Look at what they have in common instead: every buff can be applied, removed, checked for expiry and updated.

buff as its own class — composition, not inheritance
class Buff:
    def __init__(self, name, duration, amount):
        self._name = name
        self._duration = duration
        self._amount = amount

    def apply(self, character): ...
    def remove(self, character): ...
    def is_expired(self): ...
    def update(self, dt): ...

class TeamBuff(Buff):                 # a buff that hits every ally
    def apply(self, party):
        for member in party:
            super().apply(member)

class GameCharacter:
    ...
    def add_buff(self, buff):         # a character HAS buffs
        self.__buffs.append(buff)
        buff.apply(self)

    def update_buffs(self, dt):
        for b in list(self.__buffs):
            b.update(dt)
            if b.is_expired():
                b.remove(self); self.__buffs.remove(b)
Read the relationship carefully. Buff and GameCharacter are composition — a buff cannot exist on its own, and it dies with the character. TeamBuff and Buff are inheritance — a team buff is a buff. Both appear in the same small design, and picking the wrong one for either pair is the mistake the exam looks for.

This structure also absorbs the complications that always arrive later: buffs that stack (Healing +10 twice = +20), buffs that take the maximum instead (Defence +20% and +30% = 30%), and buffs that extend their own duration. Each is a rule inside Buff — not a new if in three character classes.
