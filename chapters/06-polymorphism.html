Abstraction & polymorphism

Poly + morph — many forms. One method name, many bodies, and the object decides which one runs. This is the pillar that deletes the if/elif chains.

  • Explain both meanings of abstraction and give an example of each
  • Replace a type-switch with polymorphic dispatch, and say what that buys
  • Use ABC and @abstractmethod to force a subclass to keep its promise
  • Implement __str__, __add__ and __radd__ correctly
  • Choose between inheritance and composition for a given requirement

6.1 — Abstraction has two meanings

From Latin abs (away from) and trahere (to draw): to remove detail until only what matters is left. In OOP the word carries two distinct ideas, and you need both.

1 · Interface, not implementation

Treat a class as a black box: you put a message in and get a result out, without knowing how it works inside. This is the same idea as encapsulation, viewed from outside.

Payoff: you can change the inside of a module freely, and nothing else breaks — as long as the interface stays the same.

2 · Draw the common part out

Several classes share behaviour, so lift it into one place. This is the idea that produces inheritance, and it is where abstract base classes come from.

Payoff: the shared rule has one home, and the specific parts stay with the classes that are specific.

6.2 — Polymorphism

You have used it since your first week of Python without noticing. The * operator does something different to numbers, strings and lists; len() works on anything that knows its own length. Same name, different behaviour per type.

polymorphism you already use
3 * 4          -> 12            # multiply
'ab' * 3       -> 'ababab'      # repeat
[0] * 3        -> [0, 0, 0]     # repeat the list

len('hello')   -> 5
len([1, 2, 3]) -> 3
len({'a': 1})  -> 1

In your own code it looks like this. Press Run the game loop, then add a new character class and watch which side has to change.

Polymorphism requires inheritance. The loop can safely write c.attack() only because every element is a GameCharacter and therefore promises that method. Shared interface first; different bodies second. Without the shared parent you are back to hasattr() checks and hope.
the classic example: one play() per file type
class AudioFile:
    def __init__(self, filename):
        if not filename.endswith(self.ext):
            raise ValueError('Invalid file format')
        self.filename = filename

class MP3File(AudioFile):
    ext = 'mp3'
    def play(self):
        print(f'playing {self.filename} as mp3')

class WavFile(AudioFile):
    ext = 'wav'
    def play(self):
        print(f'playing {self.filename} as wav')

class OggFile(AudioFile):
    ext = 'ogg'
    def play(self):
        print(f'playing {self.filename} as ogg')

for f in [MP3File('a.mp3'), WavFile('b.wav'), OggFile('c.ogg')]:
    f.play()        # one call site, three different decoders

Note that the subclasses have no constructor — they use the parent's, which validates the extension against each subclass's own ext class attribute. One constructor, three behaviours: polymorphism again.

6.3 — Abstract base classes

In the code above, nothing forces a new subclass to define play(). Forget it, and the program crashes at the moment somebody tries to play that file — possibly in front of a user. An abstract base class moves that failure to the moment the object is created.

abstract methods and abstract properties
from abc import ABC, abstractmethod

class MediaLoader(ABC):

    @property
    @abstractmethod
    def ext(self):                 # subclasses must define this attribute
        ...

    @abstractmethod
    def play(self):                # and this method
        ...

class Ogg(MediaLoader):
    ext = '.ogg'                   # required
    def play(self):                # required
        print('playing ogg')

o = Ogg()        # fine — both promises kept

Two rules follow from inheriting ABC:

  • The abstract class itself can never be instantiated. MediaLoader() raises TypeError — and that is correct, because “a media loader” is not a thing, it is a category.
  • Any subclass that leaves an @abstractmethod unimplemented cannot be instantiated either.
What it is really for: a uniform interface. Once Gold and Silver both inherit from an abstract Member that declares discount(), the billing code can hold any member and call discount() without checking anything.

Duck typing — and why we still use ABC

Python does not require the inheritance. If an object has a play() method, the loop will call it — “if it walks like a duck and quacks like a duck”. That flexibility is real, and it is why Python code often works with classes that share no ancestor.

Prefer the abstract base class anyway when the shared interface is part of the design. It documents the contract, it fails early, and it tells the next reader that these classes are meant to be interchangeable. In the labs, where the staff check the design, make the contract explicit.

6.4 — Magic (dunder) methods

Your classes can take part in Python's own syntax: +, len(), in, indexing, printing. These are implemented by dunder methods, and they are polymorphism applied to operators.

a Length class that adds across units
class Length:
    __metric = {'mm': 0.001, 'cm': 0.01, 'm': 1.0, 'km': 1000.0,
                'in': 0.0254, 'ft': 0.3048, 'yd': 0.9144}

    def __init__(self, value, unit='m'):
        self.value = value
        self.unit = unit

    def converse2metres(self):
        return self.value * Length.__metric[self.unit]

    def __str__(self):                       # print() -> metres
        return f'{self.converse2metres()} m'

    def __repr__(self):                      # the REPL -> as entered
        return f"Length({self.value}, '{self.unit}')"

    def __add__(self, other):
        if isinstance(other, Length):
            result = self.converse2metres() + other.converse2metres()
        else:                                # plain number = metres
            result = self.converse2metres() + other
        return Length(result)

    def __radd__(self, other):               # makes sum() and 5 + L work
        return self.__add__(other)

print(Length(3, 'ft') + Length(4, 'in'))     # 1.0160 m
print(Length(3, 'ft') + 2)                   # 2.9144 m
print(sum([Length(1), Length(2), Length(3)]))  # 6.0 m
Why __radd__ is needed. For a + b, Python first asks a.__add__(b). With 5 + Length(1), a is an int, which has never heard of Length and returns NotImplemented. Python then asks the right-hand operand via __radd__. Without it, sum() fails — because sum() starts at 0 + first_item.

6.5 — Composition: the alternative to inheritance

Inheritance is not the only way to reuse code, and it is usually not the best. Composition means holding another object and delegating to it. The guideline, in this course and in industry, is favour composition over inheritance.

Choosing correctly

6.6 — Worked example: the media player

The brief. Songs have a title, artist, album and file type (.mp3, .flac, .aac), each played by its own decoder. Podcast episodes have an episode number, title, channel, channel owner and file type. Listeners build playlists that may mix songs and podcasts. The player must play one item, walk a playlist, walk an album, search by song or album title, and add items to any of several playlists.

  1. One interface for anything playable. Media declares play() as abstract; Song and Podcast inherit it. Format-specific decoding overrides play().
  2. Albums, playlists and podcasts all hold media. All three had an add_song method, which is the signal to lift a common parent — call it Collection.
  3. Album differs by one thing: it has an artist. So Album and Playlist both inherit Collection, and only Album adds the artist.
  4. Collection holds Media by aggregation — removing a playlist must not delete the songs.

Six classes. Remember the diamond: a playlist has media, it does not own it.
the shape of the answer
from abc import ABC, abstractmethod

class Media(ABC):
    def __init__(self, title, file_type):
        self._title = title
        self._file_type = file_type

    @abstractmethod
    def play(self): ...

    def get_title(self):
        return self._title


class Song(Media):
    def __init__(self, title, artist, file_type):
        super().__init__(title, file_type)
        self.__artist = artist

    def play(self):
        return f'♪ {self._title} — {self.__artist} [{self._file_type}]'


class Podcast(Media):
    def __init__(self, title, episode, channel, file_type):
        super().__init__(title, file_type)
        self.__episode = episode
        self.__channel = channel

    def play(self):
        return f'🎙 EP{self.__episode} {self._title} — {self.__channel}'


class Collection:
    def __init__(self, name):
        self._name = name
        self._items = []            # aggregation: media live elsewhere too

    def add_media(self, media):
        if not isinstance(media, Media):
            return 'Error'
        self._items.append(media)
        return 'Done'

    def play_all(self):
        return [m.play() for m in self._items]   # polymorphism


class Album(Collection):
    def __init__(self, name, artist):
        super().__init__(name)
        self.__artist = artist


class Playlist(Collection):
    pass


mix = Playlist('Study mix')
mix.add_media(Song('Clair de Lune', 'Debussy', '.flac'))
mix.add_media(Podcast('OOP in practice', 12, 'DevCast', '.mp3'))
for line in mix.play_all():
    print(line)

Look at play_all(): one list comprehension plays a song and a podcast, in two different file formats, with no type check anywhere. That is the whole point of the chapter.
