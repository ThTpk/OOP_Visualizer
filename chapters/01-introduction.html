CHAPTER 1 · WEEK 1

Why object-oriented programming exists

Before any syntax: the specific kind of pain OOP was invented to remove, what you pay for it, and where every diagram in this course fits into building real software.

  • Explain, with an example, the failure mode that procedural code hits as a program grows
  • Name the four pillars and the problem each one solves
  • Place use case, sequence and class diagrams in the development process
  • Recognise the cases where OOP is the wrong tool

1.1 — The problem, before the solution

Imagine an online game with 5,000 characters. Each one has a name, job, level, exp, str, agi, vit, int, hp, sp, atk, def — and an outfit, and an inventory, and a guild. Now write that procedurally. You get one list per field, and every list must stay exactly the same length, in exactly the same order, forever.

It works. For a while. Then somebody deletes a character from one list and forgets the other eleven.

This is the whole argument. Objects do not make your program faster, shorter, or cleverer. They make one fact live in exactly one place. Every principle in the next nine chapters is a different application of that same idea.

So what is an object?

Something with both attributes (what it knows) and behaviour (what it can do). That test is surprisingly reliable:

ObjectAttributes — what it knowsBehaviour — what it does
Carcolour, brand, model, top speedstart engine, accelerate, brake
Smartphonemodel, screen size, battery capacitymake a call, take a photo, power on/off
Smart TVbrand, model, screen size, current channel, volume, input sourceturn on/off, change channel, change volume, change source
Bank accountaccount number, owner, balancedeposit, withdraw, transfer

Systems are made of several of these working together. A registration system has Student, Teacher, Subject, Classroom. A banking app has Account, Customer, Transaction. Facebook has User, Page, Group, Post, Comment.

A rule of thumb you will use all term. If it has both attributes and behaviour, it is an object. If it only has data, it may be a value, not a class. If it only has behaviour, it may be a function.

1.2 — The four pillars, and the problem each one solves

Learn these as answers, not definitions. In the exam and in the mini-project you will be asked which one applies, which is a different skill from reciting what they mean.

week 3

Encapsulation

Bundle data with the code that guards it, and block direct outside access.

Without it: any line in the program can put the object into an impossible state, and you will never find out which one did.

week 6

Abstraction

Expose the interface, hide the implementation. Also: lift what is common into one place.

Without it: changing how one module works breaks five others that were reaching inside it.

week 5

Inheritance

A specific class takes everything a general class has, and adds its own specifics.

Without it: the same rule is copy-pasted into eight files and updated in seven.

week 6

Polymorphism

One method name, many bodies, chosen by the object itself.

Without it: an if/elif chain that grows every time the business adds a product — in every function that touches it.

What you actually get

  • Code reuse — extending and modifying a program becomes addition rather than surgery.
  • Easier development, testing and maintenance — you can test one class without booting the whole system.
  • Explainable to non-programmers — “an Account has a balance and can be debited” is a sentence a bank manager can check. arr[3][7] is not.

And what you pay

Be honest about this, because the exam will ask you to justify a design, not to praise OOP.

  • More files, more indirection. A three-line script becomes three classes. For a three-line script, that is a loss.
  • Design decisions up front. Getting the class split wrong is far more expensive than getting a function wrong.
  • Over-engineering is a real failure mode. An abstract base class with exactly one subclass is a liability, not a credential.

1.3 — Where each diagram belongs

This course teaches three UML diagrams. They are not three ways of drawing the same thing — each answers a different question, at a different stage.

The same seven stages as a table, with the week each output is taught:

StageQuestion it answersOutputWeek
RequirementsWhat is this software for?Software specification (prose)7
AnalysisWho uses it and what can they do?Use case diagram + descriptions7
Design — behaviourIn what order do objects talk to each other?Sequence diagram8
Design — structureWhich classes exist and how do they relate?Class diagram4
Coding—Python that mirrors the class diagram2–10
TestingDoes it do what was specified?Unit → integration → UATlabs
DeploymentHow does it reach users, often?DevOps pipeline—
A question that comes up every year. “Which diagram would you draw first, and why?” The use case diagram — it defines the scope. You cannot know which classes you need until you know what the system is supposed to do. Sequence diagrams then reveal the methods, which you write back into the class diagram.

Three levels of testing

  • Unit testing — one function or one class in isolation. Encapsulation is what makes this possible at all.
  • Integration testing — the classes put together.
  • User acceptance testing (UAT) — simulating real use, with the people who asked for the system.

Modern teams automate all three as test scripts, and deploy constantly — Netflix can deploy in under a minute. That frequency is only survivable if a change to one class cannot silently break another, which is, again, what the next nine chapters are about.

1.4 — When not to use OOP

Choosing correctly includes choosing not to. Marks are lost every year by students who wrap a 30-line script in four classes because they thought that was the assignment.

✗ Classes for the sake of classes
class Calculator:
    def __init__(self):
        self.result = 0

    def add(self, a, b):
        self.result = a + b
        return self.result

c = Calculator()
print(c.add(2, 3))
The object holds no meaningful state — self.result is never read again. It is a function wearing a costume.
✓ Just a function
def add(a, b):
    return a + b

print(add(2, 3))
No state to protect, no behaviour to vary by type, nothing to inherit. A function is the correct answer.

Reach for a class when at least one of these is true:

  • There is state that must stay valid between calls (a balance, a status, an enrolment list)
  • There will be many instances of the same shape (5,000 characters, 10,000 accounts)
  • Several types must answer the same call differently (every payment method has pay())
  • You need a boundary so that outside code cannot corrupt what is inside

Do not reach for a class when you have a pure calculation, a one-off script, a simple data record with no rules (a dict or a dataclass will do), or when you are inventing an abstraction for a second case that does not exist yet.

1.5 — Check yourself

A teammate says: “OOP is better because it is more organised.” What is the sharper answer?

You must write a script that reads one CSV and prints the column averages. Nothing else. What is the right design?

Which diagram tells you how many groups of users the system has, and what each can do?
