Where this course sits in software development

An object-oriented application is not built by sitting down and typing classes. It moves through a pipeline, and almost every artefact in this course is one stage of it. When you are stuck in a lab, it is usually because you skipped a stage.

How weekly labs are actually lost. Not by failing to finish, but by breaking the standing rules: storing data outside a class, duplicating the same fact in two places, leaving an attribute public, writing input() or print() inside a class, or writing getters and setters nobody calls. Those rules are listed in full on the labs page — read them once, properly.

Assignments

Assignment 1 — Game of Life simulation

individual Pygame

Implement Conway's cellular automaton: simple rules, emergent complexity. Four rules govern every cell:

RuleConditionOutcome
Underpopulationlive cell, fewer than 2 live neighboursdies of isolation
Survivallive cell, 2 or 3 live neighbourslives on
Overpopulationlive cell, more than 3 live neighboursdies of overcrowding
Reproductiondead cell, exactly 3 live neighboursbecomes alive

Interface requirements: a grid of at least 60 × 40 cells with clear contrast between alive and dead; pause/play toggle; mouse click to toggle a cell while paused; R to clear the board; a randomise key.

Submit: main.py with a proper game loop and neighbour-counting logic, plus README.txt documenting every control.

Assignment 2 — Legacy code refactoring

individual three phases

  1. Analysis & reverse engineering. Read the supplied legacy code, reverse-engineer a UML class diagram of the mess as it stands, then compare it against the SRS to see whether it even does what was asked.
  2. Code review. Identify at least three major code smells — duplicate code, poor naming, god classes, broken encapsulation, no separation of concerns — and write a report with a specific fix for each.
  3. Refactor. Rewrite it: meaningful names, clear flow, strict compliance with the SRS, and real encapsulation, inheritance and separation of concerns.

Deliverables: the current (messy) class diagram as image or PDF; the review report as PDF; the refactored Python source.

Work chapter 10 before you start phase 2 — the SOLID chapter gives you the vocabulary that turns “this code is bad” into “Order has three reasons to change, which violates SRP.” One of those sentences earns marks.

Assignment 3 — Mini-application group project

groups of 3–5 30% of the lecture mark

Design and build a desktop application that simulates a real management system. Pick a domain:

Bank management

accounts, deposits, withdrawals, transaction history

Pet shop

animal inventory, food stock, sales, adoptions

Library system

borrowing, returns, fines, members

Student registry

enrolment, grades, GPA, records

Technical requirements: effective use of classes, inheritance and polymorphism; full CRUD; persistence to file (.txt, .csv, .json) or a database; a working GUI in tkinter, PyQt or Pygame; and a class presentation with a live demo.

Deliverables: organised source code, the UML class diagram that served as your blueprint, and presentation slides.

Homework 1 — group formation

Form a group of 4–5 students, pick an existing website or application as the prototype you will model (car rental, restaurant management, hotel rooms, library management, …), and submit your group name and members through the shared sheet given in the week 1 slides.
